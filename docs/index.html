pwn-playbooks

Playbooks for pwn-broker, read into a box's note and filled in

A playbook is one job, such as enumerating SMB or escalating through a Windows service, written as the checks and commands I work through on a box. In pwn-broker's note window, :Pb smb reads one in below the cursor. Every value I have to supply is a placeholder such as <TargetIP>, and the playbook carries the few lines of vim that fill each one in, throughout that playbook and nowhere else in the note.

Get them

tool install playbooks

At a pwn-broker 0.1.7 or later prompt. They come from pwn-shop's package playbooks, checked and pinned like any tool: release 2026.11.20.1, 79 playbooks. finish takes them off again, and a box I reopen later gets the release it was worked with.

Without pwn-broker: download playbooks-<version>.zip from the latest release, check it against SHA256SUMS.txt, unzip it, and read a playbook into any vim. Its run block works the same way.

:r playbooks/02-enum/smb.md

Reading one in, and filling it in

Reading one in

  • :Pb <name> reads the playbook with that file name into the note, below the cursor. Tab completes the name from any part of it, so :Pb kerbero finds 07-ad/kerberoasting.
  • :Pb on its own lists every playbook, by folder, to pick one by number.
  • It never lands inside the box header: on the header it reads below it, and on a closed fold below the fold. It arrives as one open fold, with the cursor on its first line to fill in.
  • Closed, the fold shows its Playbook: line: the title, the path and the release it came from.

Filling one in

The lines from my to 'y are the run block.

  1. Over each <Replace>, type the value: ca> on it removes the word and its angle brackets and starts insert mode. Delete with dd each line I am not filling yet.
  2. On the my line, V} selects the block down to its blank line, and "qy copies it into register q.
  3. @q runs it. It marks the block's first line y, finds this playbook's END OF line and marks it z, replaces each placeholder between the two, and goes back to y.

The Fill in: line keeps count

It is inside the range, so afterwards it shows the values used, and any placeholder still on it is one not yet filled. A placeholder I left out stays as it is in the body, to fill in by hand once I know it.

One playbook, two targets

The same playbook read in twice fills only the copy whose block ran: the search for its end looks only below the block. A copy whose END OF line I deleted changes nothing, unless another copy follows it.

Through a register, on purpose

Pasting the block from the terminal would only insert it as text. A value is typed into a vim replacement, so a /, &, \ or ~ in it needs a backslash in front, which matters mostly for passwords.

Search stays useful

pwn-broker's search skips a playbook's run block, and any line that still holds a placeholder, so unfilled template text never floods the results. A line I have filled in is searched like any other.

Placeholders

Every value a playbook asks for is one of these, written <Name>, one name per meaning. A value is typed into a vim replacement, so none stands for a URL or a path: a URL is split, as <Scheme>://<WebHost>, and a value to edit by hand is written in capitals, such as THE-PAGE. The list is placeholders.toml.

the target's IP address
<Domain>
the Active Directory domain, such as corp.local
<DCIP>
a domain controller's IP address
<BaseDN>
the domain's base DN, such as DC=corp,DC=local
<Username>
a username

How a release is made

  • Each playbook is a markdown file in playbooks/: a # title line, then the body, with every value as a placeholder from the list.
  • python build.py check refuses anything that would break the note: a file name used twice, a name that is not lowercase letters, digits and hyphens, a fold marker, a line the run block would stop at, a placeholder whose case is wrong, the reserved word <Replace>, and Obsidian's callouts, links and front matter. It names the file and line.
  • python build.py build --version <version> wraps each playbook in its fold and run block and zips the tree. The same tree always gives the same bytes.
  • CI runs the check and the tests on every change. They include a real vim filling in every playbook, with a realistic value for every placeholder.
  • A tag v<YYYY.MM.DD> publishes the release, with .1, .2 for a second one on the same day. pwn-shop then packages it, and installs it in the official Kali image with the network off before publishing it.
  • A published release is never changed: a fix is a new release. CONTRIBUTING.md has how to write a playbook and how a release is cut.
